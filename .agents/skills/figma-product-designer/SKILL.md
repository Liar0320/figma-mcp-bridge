# Figma 产品界面设计师

## 目标与边界

把产品语义转化为清晰、可信、可继续修改的产品界面。固化设计判断与验收，不固定所有产品的配色、字体、圆角或卡片模板。

本 skill 负责整页与流程设计，包含应用界面和公开 Landing Page 两类模式。新建组件/变体时同时读取 `skill://figma-component-creator`；规范化已有组件时读取 `skill://figma-component-normalizer`。品牌任务遵从相应品牌 skill。只有公开营销页才采用转化叙事，不因用户说“Apple 风格”就把后台页面改成营销页。

跨 skill 的读取范围以用户授权为上限。若用户禁止读取现有画面，组件 skill 中的全文件组件/样式盘点、页面边界检查改为仅针对本次新建容器；必要连接路由仍可查询。创建自包含组件并明确原始视觉值未绑定既有 token，不假称完成原文件复用。此限制不免除真实组件、原生属性绑定和新建节点验证。

设计稿、交互原型、真实业务实现是三种交付：只承诺本次实际完成的层级。用户只要求讨论时不写 Figma；用户要求绘制时应完成实际画面，而不只给建议。

## 按需阅读

- 开始 Figma 写入前：阅读 `references/figma-engineering.md`。
- 确定平台后：阅读 `references/platforms.md`，仅采用匹配平台的章节。
- 公开产品页明确要求 Apple / 苹果官网 / 极简产品发布风格时：阅读 `references/landing-apple.md`，作为本 skill 的 Landing Page 模式，不安装或新建独立 skill。
- 主页面试样与最终交付前：阅读 `references/acceptance.md`。
- 外部 UI skill 可补充建议，但必须检查是否符合产品。拒绝不适用的营销结构；外部推荐不能覆盖 brief、品牌或宿主平台要求。

## 模式选择

| 请求与使用场景 | 应用模式 |
|---|---|
| Shopify Admin、后台、设置、日志或已登录任务 | 应用界面；遵从宿主与品牌，即使提及 Apple 也不自动添加 Hero |
| 公开 Landing Page / 产品发布页，且要求 Apple-inspired | Landing / Apple-inspired；以产品证据和转化路径组织叙事 |
| 公开 Landing Page，但指定其他品牌或未指定 Apple | 保留该品牌/方向，不自动套用 Apple 配色与版式 |
| 同时包含官网和已安装应用 | 分别组织画板和规范，共享业务事实，不混合导航与 CTA |

记录采用的模式及理由。只覆盖真实需要的状态：纯展示页不制造后台任务、授权恢复或加载仪表盘；表单或购买流程存在时才补其错误与恢复。

## 工作流

### 1. 理解与取舍

先读用户给定的 brief、素材和明确相关资料。提炼：

| 设计判断 | 必须明确 |
|---|---|
| 用户与场景 | 谁在何处完成什么任务 |
| 首要任务 | 每个页面首先帮助用户做出的决定 |
| 核心对象 | 连接、任务、记录、配置等对象及关系 |
| 决策信息 | 哪些信息改变用户下一步行动 |
| 业务不变量 | 不允许误导或改变的业务规则 |
| 状态与恢复 | 空、加载、成功、处理中、失败及下一步 |
| 实现边界 | 已确认能力、目标能力、尚未确定事项 |

不要把 brief 的每段文字都变成一张卡片。先分清主信息、渐进展开信息和设计交接说明。只为用户必须决定的重大权衡提问，其余采用有依据的保守方案并说明。

禁止虚构统计、客户证言、连接状态或功能可用性。状态示例需在画板外或独立设计标识中说明；不要让设计注释挤占正常产品界面。未配置链接不制造假地址，未实现能力不得伪装成已上线。

### 2. 组织信息与确定视觉方向

列出页面、关键路径、必要状态和断点。每页用一句话回答：第一眼看哪里、主要操作是什么、次要信息去哪里。

- 总览：当前情况 → 需要处理的问题 → 最近结果。
- 设置：设置用途 → 当前值 → 修改操作。
- 任务表单：输入 → 影响范围 → 确认 → 任务状态。
- 资源列表：筛选 → 结果 → 详情 → 保留上下文地返回。
- Landing：价值承诺 → 产品主视觉/可核实证据 → 功能叙事与保护边界 → 消除疑虑 → 同一转化目标的 CTA。Apple-inspired 的构图规则见专用参考。

选定语义颜色、字阶、间距、密度与容器规则。视觉优先级依次为：产品/品牌约束、宿主平台规范、任务需要、通用审美。用字号、字重、空间和位置建立层级，不只靠颜色；卡片用于真实分组，不作统一装饰。

### 3. 先试样，再扩展

应用任务先绘制最多两个代表性页面：一个主页面，一个信息最密或状态最复杂的页面。Landing 单页面任务先做 Hero 与一个关键证据区块，并验证窄屏，再延展整页；不为凑两页制造新页面。

检查截图、任务聚焦、文案及实际布局结构。先修正主次、密度、间距、冗余提示，再扩展。除非用户明确要求审批，不因试样完成而停下来等待确认。

### 4. 提炼组件与扩展

从试样中提炼真实重复元素，建立最小够用的组件体系。不预建庞大组件库，也不把全部页面画完后才补组件。

正常内容流使用 Auto Layout；正确区分 Hug、Fill、Fixed。复用实例和统一样式/变量。绝对定位只用于浮层、遮罩、装饰叠放以及画板在交付画布上的排列。

扩展剩余页面、真实需要的业务状态和窄屏布局。应用状态板用于索引，不代替关键场景的整页设计；在真实页面上下文展示最高风险错误与恢复动作。Landing 按 brief 展示 CTA 可用/不可用、FAQ 展开/收起及实际存在的表单状态，不强加应用状态全集。

### 5. 压力验证与视觉纠正

在本次新建或明确获准修改的节点内验证，不扩大读取范围。使用可用的布局诊断、文字测量、截图及实际尺寸调整，而不是只检查创建调用成功。

所有模式至少验证长标题、窄容器和实际组件内容变化。应用继续验证长错误原因、空/加载、主操作不可用、窄屏表单与详情；Landing 验证 Hero 换行、主视觉重排、CTA 真实可用性、FAQ 展开及 reduced-motion 静态叙事（如涉及动效）。临时测试使用本次创建内容的副本或可恢复修改，完成后移除自己的测试副本或恢复基准；不删除用户节点。

若缩窄宽度或增加文案导致布局失效，修复约束与结构，不能仅缩小字号或截断关键原因。截图检查发现视觉层级弱或内容冗余时，可以调整页面结构，不限于修裁切。

### 6. 交付

交付实际可编辑的 Figma 节点。产品界面、组件/样式区、设计注释分开组织。给出容器名称、节点 ID、可验证的链接（工具能提供时）和截图路径。

说明完成的页面/状态、实际验证项及未验证边界。不能把静态设计说成已完成键盘交互、OAuth、轮询或业务同步。工具阻塞时明确已完成的真实部分和缺失能力，不用截图贴图冒充可编辑结构。

## 核心质量门槛

- 用户无需阅读交接注释就能理解主要任务和下一步。
- 一个任务区域只有一个突出主操作。
- 颜色表达语义，不制造满屏告警；状态同时有文字。
- 数据未知不显示为已确认的 0；提交成功不等于任务完成。
- 重复元素可统一修改；长内容和窄容器下布局仍成立。
- 不把“图层可编辑”等同于“具有响应式约束”。
- 截图是设计反馈工具，不只是交付附件。
