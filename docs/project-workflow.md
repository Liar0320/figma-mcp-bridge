# Figma MCP Bridge 工作流

本文件规定本仓库的需求归属与交付方式。它不替代 [开发与验证说明](development-workflow.md)、[贡献指南](../CONTRIBUTING.md) 和仓库的 `AGENTS.md`；代码、协议和插件运行时的具体约束以这些文件为准。

## 归属与规划

- **GitHub Issues：统一待办。** CLI、MCP server、Figma plugin、设计令牌、文档和维护工作都在本仓库的 [Issues](https://github.com/Liar0320/figma-mcp-bridge/issues) 中记录。标题描述结果；正文说明问题或背景、预期行为、范围以及可以实际验证的完成条件。未知的实现细节写成待调查问题，而不是假定已有方案。
- **GitHub Projects：可选的多 issue 规划。** 仅当一项交付需要协调多个可独立验收的 issue 时使用；小任务直接用 issue。不要为了单个任务建立 Project，也不要同时维护两套状态。
- **子 issue：** 仅在部分工作能独立实施或独立验收时拆分；不要机械地按“代码、测试、文档”拆票。

CLI 入口可以先作为一个 issue 记录；如实施需要多项独立交付，再拆分 issue 并视需要用 Project 协调。插件 UI 版本号展示是另一个独立 issue，不从属于 CLI。

## 从需求到完成

1. **记录：** 在本仓库建 GitHub issue；若需求尚未明确，先记录现状、期望和开放问题，不承诺实现方案。相关设计文档用链接关联，不复制维护两份状态。
2. **决定范围：** 开工前明确本次交付、不做什么以及如何验收。跨 server/plugin 协议、公开工具契约、数据迁移或存在重要方案取舍时，先把设计决策和风险写在 issue 或独立设计文档；小型改动不强制另写规格或审批材料。
3. **实施：** 按仓库已有约定提交变更并关联 issue。需要 PR 时在 PR 中说明行为、风险和验证证据；不为流程本身制造无价值的子任务。
4. **验收：** 完成条件全部满足后再关闭 issue。运行相关构建/测试，并实际操作变更路径；插件运行时代码必须在构建后重启 Figma 中的 Figma MCP Bridge 插件并验证。必要时更新用户文档。无法验证的项目明确记录原因，不标记为已验证。

GitHub Issues 记录待办、范围和执行状态；代码与运行验证代表当前实现，仓库文档记录长期行为。定期查看未关闭的 issue；仅在需要协调多项独立交付时使用 GitHub Projects。
